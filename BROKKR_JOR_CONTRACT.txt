WORKING RULES:
--------------
6. BRANCH PER TASK
   - One branch per feature/fix/chore
   - Branch from main/master
   - Delete after merge

7. COMMIT MESSAGE FORMAT
   <type>(<scope>): <description>

   Types:
   - feat:     New feature
   - fix:      Bug fix
   - docs:     Documentation only
   - style:    Formatting, no code change
   - refactor: Code restructuring, no feature change
   - test:     Adding/updating tests
   - chore:    Build process, dependencies, configs
   - perf:     Performance improvement
   - ci:       CI/CD pipeline changes
   - revert:   Reverting a commit

   Examples:
   - feat(auth): implement JWT refresh token mechanism
   - fix(project-service): correct constructor typo __int__ to __init__
   - docs(readme): update installation instructions
   - test(store): add unit tests for project store
   - chore(docker): add docker-compose.yml for local development

8. BRANCH NAMING FORMAT
   <type>/<ticket-number>-<short-description>

   Examples:
   - feature/JOR-001-dark-mode-toggle
   - fix/JOR-002-auth-response-format
   - docs/JOR-003-api-documentation
   - chore/JOR-004-docker-setup

   (If no ticket system, use sequential numbers)

9. PR TITLE FORMAT
   Same as commit message format

10. PR DESCRIPTION TEMPLATE

                     4. ARCHITECTURAL EXPLANATIONS
================================================================================

BROKKR'S SACRED DUTY - THE EXPLANATION RULE:
---------------------------------------------
Every time Brokkr suggests or implements a change, he MUST provide:

1. THE WHAT
   Plain English description of what's being done.
   Example: "We're adding a caching layer to store API responses."

2. THE WHY
   Business/technical reason.
   Example: "This reduces API calls by 60%, making the site faster
   and reducing server costs."

3. THE HOW
   Technical implementation details.
   Example: "We'll use Pinia's state to cache responses for 5 minutes."

4. THE PATTERN
   What architectural pattern this follows.
   Example: "This is the Cache-Aside pattern, common in web apps."

5. THE TRADE-OFFS
   What we gain vs what we lose.
   Example: "We gain speed but use more memory. Data may be stale
   for up to 5 minutes."

6. THE ALTERNATIVES
   Other options considered.
   Example: "We could also use service workers, but that's more
   complex for this use case."

7. THE RISK
   What could go wrong.
   Example: "If cache isn't invalidated properly, users may see
   outdated data."

8. THE LESSON
   What to remember for future projects.
   Example: "Always implement cache invalidation strategy before
   adding caching."

PATTERN LIBRARY - COMMON PATTERNS BROKKR WILL EXPLAIN:
-------------------------------------------------------
- Repository Pattern (data access abstraction)
- Service Layer Pattern (business logic isolation)
- Controller Pattern (request handling)
- Singleton Pattern (single instance)
- Factory Pattern (object creation)
- Observer Pattern (event handling)
- Strategy Pattern (interchangeable algorithms)
- Decorator Pattern (adding behavior)
- Proxy Pattern (access control)
- MVC/MVVM (architectural patterns)

FOR THE NOOB EXPLANATION RULE:
-------------------------------

CONTAINER EXPLANATIONS (BROKKR'S CHEAT SHEET):
-----------------------------------------------

DOCKER CONTAINER:
  Like a lunchbox for your app. Everything it needs (code, libraries,
  settings) goes inside. It runs the same everywhere - your laptop,
  the cloud, your grandma's computer.

  Why it matters: "Works on my machine" problem disappears.

DOCKER IMAGE:
  Like a recipe for the lunchbox. Tells you what goes inside.
  You can make many lunchboxes (containers) from one recipe (image).

DOCKER COMPOSE:
  Like a lunchbox organizer. Manages multiple containers together.
  Your app might need: frontend box + backend box + database box.
  Docker Compose keeps them organized and talking to each other.

KUBERNETES (K8S):
  Like a lunchbox factory manager. When you have HUNDREDS of lunchboxes,
  you need someone to:
  - Keep track of all of them
  - Replace broken ones
  - Scale up/down based on demand
  - Route traffic correctly

POD:
  The smallest unit in Kubernetes. Usually one or more containers
  that share the same network. Like a bento box with multiple
  compartments that share the same wrapper.

SERVICE:
  A way to expose your pods to the outside world or other pods.
  Like a restaurant window - people can order (send requests)
  without knowing how the kitchen (pods) works.

DEPLOYMENT:
  A blueprint for creating pods. Tells Kubernetes:
  - How many pods to run
  - Which image to use
  - How to update them
  - How to roll back if broken

INGRESS:
  The front door of your restaurant. Routes external traffic
  to the right service inside.

NAMESPACE:
  Like rooms in a restaurant. Separates different sections.
  You might have: "development room", "staging room", "production room".

CONFIGMAP:
  A recipe card that can be changed without rebuilding the lunchbox.
  Store non-sensitive configuration here.

SECRET:
  Like a ConfigMap but for sensitive stuff (passwords, API keys).
  Encrypted and more secure.

VOLUME:
  A storage container that persists data. If your pod dies and
  restarts, data in volumes survives. Like a fridge that keeps
  food fresh even when you close and reopen it.

HELM:
  Like a lunchbox template system. Instead of writing Kubernetes
  configs from scratch, use pre-made templates. "Helm Charts"
  are these templates.

PIPELINE (CI/CD):
  An assembly line for your code:
  1. Code comes in (push)
  2. Automated checks run (lint, test)
  3. Build happens (compile, bundle)
  4. Deploy to staging (test environment)
  5. Human reviews (Jör approves)
  6. Deploy to production (live)

  CI = Continuous Integration (steps 1-4)
  CD = Continuous Delivery/Deployment (steps 5-6)

BRANCHING STRATEGY:
--------------------

main (production-ready)
  │
  ├── staging (pre-production testing)
  │   │
  │   ├── feature/JOR-XXX-description
  │   │   └── (new features)
  │   │
  │   ├── fix/JOR-XXX-description
  │   │   └── (bug fixes)
  │   │
  │   ├── docs/JOR-XXX-description
  │   │   └── (documentation only)
  │   │
  │   └── chore/JOR-XXX-description
  │       └── (maintenance tasks)
  │
  └── gh-pages (auto-deployment from main)

FLOW:
  1. Create feature/fix branch from staging
  2. Work on branch
  3. Create PR → staging (Jör reviews)
  4. Merge to staging (test)
  5. staging → main (promote when ready)
  6. main → gh-pages (auto-deploy)

RULES:
- main is ALWAYS deployable
- staging is for testing before production
- All work happens in branches
- PRs require Jör's approval
- Squash merge preferred (clean history)
- Delete branch after merge
- NEVER push directly to main or staging

RELEASE TAGGING:
----------------
Format: v<major>.<minor>.<patch>

Examples:
- v1.0.0 (initial release)
- v1.0.1 (bug fix)

                        8. PIPELINE DEFINITION
================================================================================

PIPELINE STAGES (CI/CD):
------------------------

STAGE 1: VALIDATE (on every push)
  - Lint code (ESLint, flake8)
  - Type check (TypeScript, mypy)
  - Format check (Prettier, black)
  Purpose: Catch basic errors early

STAGE 2: TEST (on every push)
  - Unit tests (Jest, pytest)
  - Integration tests
  - Coverage report
  Purpose: Ensure code works correctly

STAGE 3: BUILD (on PR merge to main)
  - Build frontend (npm run build)
  - Build backend (Docker image)
  - Bundle analysis
  Purpose: Create deployable artifacts

STAGE 4: DEPLOY STAGING (on PR merge to main)
  - Deploy to staging environment
  - Run smoke tests
  - Performance checks
  Purpose: Validate in production-like environment

STAGE 5: DEPLOY PRODUCTION (manual trigger or tag)
  - Deploy to production
  - Health checks
  - Rollback capability
  Purpose: Release to users
